# SillyTavern 桌面聊天客户端 — 需求拆解文档（v1.0）

> 阶段一产出 · 2026-09-21 定稿 · 状态：已确认

## 1. 项目概述

**核心目标**：将 SillyTavern 以"聊天软件"的形式在前台展示，界面参考微信方向。本质是对 SillyTavern 进行二次开发，套一层聊天工具 UI。

**定位**：基于 Tauri 的桌面端聊天客户端，SillyTavern 作为后端服务内置。

## 2. 技术方向

| 项 | 方案 |
|---|---|
| 应用框架 | Tauri（Rust + Web 前端） |
| 前端 | 自研聊天 UI（仿微信形态），不嵌入 ST Web UI |
| 后端 | SillyTavern 作为 Sidecar 子进程运行，前端通过 ST API 通信 |
| ST 原 UI | 纯后端不暴露，所有设置/管理通过自研前端实现 |

**Sidecar 评估结论**：可行，不构成对前端能力的捆绑。前提是把 ST 定位为纯后端服务 + API。设计阶段需先盘点 ST API 能力清单，确认前端功能都有接口支撑，缺口处补接口或前端绕开。

### 2.1 插件化架构方向

- 参考"万物可插件"思路（类似 DeepSeek harness 的插件化理念）
- **已决策**：首版采用"最小可接入插件"实现——以最小代价接入 ST 现有扩展，验证可行性
- 预留自建插件体系演进路径：若最小接入方案受限，后续自建插件规范
- 后续（配合开源）：开放皮肤 / 主题、功能插件等扩展点，形成插件生态

### 2.1 插件化架构方向（新增）

- 参考"万物可插件"思路（类似 DeepSeek harness 的插件化理念），整体架构按可扩展设计
- **首版**：支持 ST 扩展 / 插件的加载与基础管理；前端架构预留扩展点
- **后续**（配合开源）：开放皮肤 / 主题、功能插件等扩展点，逐步形成插件生态

## 3. 平台策略

- 首版：Windows 优先跑通
- 后期：推进跨平台（macOS / Linux）
- 选型约束：Tauri 与前端框架均需保证跨平台能力

## 4. 核心概念模型

| 聊天软件概念 | 映射到 SillyTavern |
|---|---|
| 联系人 | 角色卡（一张角色卡 = 一个联系人） |
| 会话列表 | ST 会话（每个会话由背景 + 世界书 + 角色等配置定义） |
| 单聊/群聊 | 不做区分，会话是"配置驱动"的实体 |

前端两大核心结构：**会话列表（可切换）** + **角色卡管理（联系人体系）**，会话本身可配置角色、世界书等。

## 5. 使用场景与分发

- 不做账号体系
- 首要：个人本地自用
- 后续：考虑开源
- 不涉及云 / 更新推送 / 多用户管理

## 6. 首版功能范围

**原则**：首版即保证可使用全部 SillyTavern 基础功能（非最小 MVP，而是 ST 基础功能的完整前端化）。

### 6.1 对话与消息
- 发送消息 / 接收流式回复
- 消息气泡展示（用户 / AI 区分）
- 重新生成 / 编辑 / 删除消息
- 消息分支（ST swipe）

### 6.2 会话管理
- 左侧会话列表
- 新建 / 切换 / 删除 / 重命名会话
- 会话配置（角色 + 世界书 + 背景）

### 6.3 角色卡管理（联系人）
- 角色卡列表
- 导入 / 导出
- 编辑角色卡
- 角色卡详情查看

### 6.4 世界书
- 世界书列表
- 编辑 / 条目管理
- 挂载到会话

### 6.5 预设与 Prompt
- 预设管理
- Prompt 模板
- 采样参数调整

### 6.6 API 与模型
- API key 配置
- 模型选择
- 连接测试

### 6.7 用户 Persona
- 用户人设管理

### 6.8 扩展与插件系统（含记忆）
- 记忆能力：总结记忆（Summarize）、向量存储 / 检索（Vector Storage）、作者注释（Author's Note）
- ST 扩展 / 插件的接入与管理（首版按"最小可接入"实现，见 2.1）
- 插件化架构预留扩展点，后续开放皮肤 / 主题等

> ✅ 上述清单已由项目所有者确认（2026-09-21）。

## 7. 待解决问题

| 问题 | 说明 | 计划 |
|---|---|---|
| ST API 能力盘点 | 确认前端每个功能有接口支撑（含记忆 / 扩展接口） | 设计阶段做 |
| 插件体系路线 | 兼容 ST 现有扩展生态 vs 自建插件规范，随 API 盘点一并评估 | 设计阶段 |
| 数据存储方案 | 会话历史 / 角色卡存哪、前端是否额外存 | 设计阶段 |
| 前端框架选型 | React / Vue / Svelte，需兼顾跨平台、开发效率与插件化支撑 | 设计阶段定 |
