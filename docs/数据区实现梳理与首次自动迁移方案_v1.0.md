## 一、原设计（S2 · 数据区外移）

```
代码（可随版本替换）   <ST目录>/                      ← server.js / node_modules / public
数据（永久保留）       <应用配置目录>/st-runtime/data  ← 角色卡 / 会话 / 密钥 / 世界书
配置                  <应用配置目录>/st-runtime/config.yaml
```

靠 ST 的 `--dataRoot` / `--configPath` 实现。目的：升级 ST 不丢数据 + 为 macOS 只读包体铺路。

## 四、根因链（为什么 `--dataRoot` 一直没生效）

```
① autobind 写入 data_root = <config>/st-runtime        （此时目录还不存在）
        ↓
② data_paths() 第 681 行 if pb.is_dir() → false
        ↓
③ 静默回退 → data_root = <st_dir>/data
        ↓
④ st_sidecar.rs:164 条件 data_root != st_dir/data → 相等 → 不传 --dataRoot
        ↓
⑤ ST 用默认值 ./data → 数据写进代码目录
        ↓
⑥ 同时 configPath 分支生效（先建父目录）→ 把 st-runtime 空目录造了出来
```

**一个自杀式循环**：目录不存在 → 回退 → 不传参 → ST 用默认 → 目录始终建不起来（直到别的分支顺带造出它）。

## 五、口径不一致（另一处隐患）

| 用途 | 函数 | 值 |
|---|---|---|
| autobind 落绑定 | `external_root()` | `st-runtime` |
| 迁移引擎 / 状态展示 | `external_data_root()` | `st-runtime\data` |

两者差一层。若只修好传参而不统一口径，第二次运行 ST 会把 `default-user` 直接写在 `st-runtime\` 根下，与 `config.yaml` 混在一起，**不符合 S2 的 `{data, config.yaml}` 布局**。

## 六、老板要的机制

> 用户首次挂载 ST 时，把 ST 目录里的 data **自动同步**到 `st-runtime\data`；
> 之后新建/导入角色卡、创建会话、配密钥，全部落在 `st-runtime\data`，不再读 ST 目录下的角色卡。

**这不是从零加机制——迁移引擎已在，缺的只是把它接进自动流程。**
